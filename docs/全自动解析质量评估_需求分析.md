> 配套文档：`docs/rules-prompts.md`（站外结构化提示词真源）、`docs/AI智能录题_需求分析.md`（录题流水线）、`src/ai/slice/`（全自动切片与清洗）。

> **本文档版本**：v1.0 · 2026-08-26
>
> **约束**：本轮只产出需求规格，**不改动系统代码、接口、脚本或提示词**。后续实现须另开任务，并与本文档逐条对照。

## 0. 文档定位

| 项 | 说明 |
|---|---|
| 本文档作用 | 定义「全自动解析 vs 站外结构化」质量评估闭环：测什么、怎么比、分数怎么用、失败怎么分流到代码或提示词 |

| 读者 | 开发、教研、后续写评测工具的人 |

## 1. 背景与问题

### 1.1 两条录入路径

系统对同一份试卷有两条结构化路径，**Stage 1 OCR 相同**，Stage 2 不同：

| 路径 | `pipeline` | Stage 1 | Stage 2 | 结果落点 |
|------|------------|---------|---------|----------|
| 全自动 | `full` | MinerU 等 OCR → `ocr_markdown` | 规则切块 + 高置信跳过 + 剩余题批量 LLM + `recover` + `slice::polish` | `progress.staged_questions[].parsed` |
| 站外结构化 | `ocr_export` | 同上，OCR 完成后停止 | 用户按 `docs/rules-prompts.md` 把 Markdown 交给外部模型，再 `POST /ai/parse-task/{id}/import-questions` | 同上，`parsed` 来自导入 JSON |

两条路径最终都产出暂存题 `ParsedQuestion`，**用户点保存之前不会写入 `questions` 表**。

### 1.2 为什么要评估

全自动路径已做切片清洗、放宽跳过、批量 Stage2、从 Markdown 回填解析等优化，压测显示耗时和 LLM 调用次数明显下降。但：

1. **速度不等于结构正确**。跳过率升高后，规则切错、选项未剥离、答案字母漏提、小问未入 `parts`、【分析】/【点睛】残留等问题可能被掩盖。
2. **站外路径不是黄金标准**。它只是同一份提示词约束下的另一种 LLM 输出；提示词本身也可能与卷面事实不一致。
3. 需要一套**可重复、可分流**的对照，把失败归到「切片/回填代码」或「提示词规则」，避免凭感觉改正则或改 prompt。

### 1.3 一句话目标

> 同一用户、同一 `document_id`、同一份 `ocr_markdown` 上跑全自动与站外两条流水线，导出暂存 JSON，按题号对齐后打分；分数用来改全自动实现和（必要时）提示词，而不是给模型排名。

## 2. 目标与非目标

### 2.1 目标

1. **可复现对照**：同一 OCR 文本上得到两份 `ParsedQuestion[]`，不因重复 OCR 引入版面差异。
2. **卷面为事实**：MinerU Markdown 是纸面事实源；两份 JSON 都是「对 Markdown 的结构化候选」，任何一方都可以错。
3. **硬检查 + 有限 LLM 裁判**：能用规则判定的结构问题必须用脚本判定；LLM 裁判只用于「解析是否忠实于原文」等语义保真。
4. **失败可分流**：每条失败落到明确桶，并映射到改代码还是改 `rules-prompts.md`。
5. **回归集固定**：以当前 10 份解析卷（约 206 题）为第一期回归集；后续增卷须显式加入清单，不得 silently 换样本。
6. **裁判不得自动改系统**：评测输出是报告与待办夹具，不直接改 prompt、正则或 worker。

### 2.2 非目标（本期明确不做）

- ❌ 不为评测再开第二个账号、再传一遍 PDF（文档按用户隔离，会触发第二次 OCR，对照失效且浪费配额）。
- ❌ 不把已保存进库的 `questions` 当作评估对象（编辑、打标、审核会污染结构）。
- ❌ 不把站外 JSON 当作 ground truth 自动「纠正」全自动结果。
- ❌ 不评估知识点 / 章节 / 解题方法打标准确率（打标默认暂停，`MATHSET_ENABLE_TAGGING=1` 才恢复；评估轴是结构与原文保真）。
- ❌ 不改 `ocr_export` 导入协议、不改站外提示词，除非评估闭环已经证明「两边相对 Markdown 犯同一类错」且责任在提示词。
- ❌ 不把评测做成产品功能（教师端 UI、排行榜、自动审题）。
- ❌ 本期不要求补齐 LLM `usage` token 统计（可选后续；不影响结构质量结论）。

## 3. 硬约束（实现时不得破坏）

| ID | 约束 | 说明 |
|----|------|------|
| C1 | 站外路径行为不变 | `pipeline=ocr_export`、复制 Markdown、按 `rules-prompts.md` 导入的流程与 JSON 契约保持可用；评测不得为图方便改导入格式 |
| C2 | 同一 OCR | 对照必须共享 `document_id` 上的 `ocr_markdown`；禁止「两个用户各传一次」或「全自动跑完再对 PDF 重做 OCR」 |
| C3 | 评估暂存题 | 只读 `staged_questions[].parsed`（及任务级 `ocr_markdown`）；不读、不写已保存题目 |
| C4 | 打标默认关闭 | 与当前全自动策略一致；评测样本上不应依赖异步打标结果 |
| C5 | 日配额 | 每用户解析任务约 50 次/日；评测设计须能复用已有 OCR 任务，避免把配额打满 |
| C6 | 裁判只出报告 | 任何 LLM judge 不得写回 `docs/rules-prompts.md`、不得改 `src/ai/slice`、不得改 worker |
| C7 | 提示词真源 | 站外提示词以 `docs/rules-prompts.md` 为准，并与代码中的 `CORE_PARSE_RULES` 保持测试对齐；改提示词是评估结论驱动的独立变更，不是评测脚本的副作用 |

## 4. 评估设计

### 4.1 实验单元

一次对照实验的最小完整单元是：

```text
同一 user_id
  └── 同一 document_id          ← 只 OCR 一次
        ├── ocr_markdown        ← 唯一事实源
        ├── task_full           ← pipeline=full，产出 staged_A
        └── task_export         ← pipeline=ocr_export + import，产出 staged_B
              └── 按 question_no 对齐后的题对 (A_i, B_i, md_i)
```

- **一份文档对应一次 OCR**。全自动任务与站外任务必须能指向同一 `document_id`（或等价地：站外任务直接复用已写入的 `ocr_markdown`，不再调 MinerU）。
- **一份文档对应两份暂存数组**，不是两份题库记录。
- 题对的第三元是该题在 Markdown 中的切片（或整卷 Markdown + 题号定位），供硬检查与裁判引用。

### 4.2 为什么必须同一用户

`documents` / 解析任务按创建者隔离。换账号意味着重新上传、重新 OCR，版面、公式、题号切分都可能变，对照失去意义，且 OCR 成本翻倍。

### 4.3 任务怎么开（需求层，非实现）

实现阶段允许两种等价策略，需求只要求**共享 Markdown、两次结构化**：

| 策略 | 做法 | 要求 |
|------|------|------|
| A. 两任务同文档 | 已有 `document_id` 上再提交一条 `pipeline=ocr_export` 或 `pipeline=full` | Worker 必须识别「该文档已有 OCR」并跳过重复识别，直接进入对应 Stage 2 |
| B. 导出后再导入 | 从已完成的 `full` 任务取出 `ocr_markdown`，构造/复用 `ocr_export` 任务并 import | 导入所用 Markdown 字节级等于全自动任务中的 `ocr_markdown` |

现状：`GET /ai/parse-task/{id}` 已能返回 `ocr_markdown` 与 `staged_questions[].parsed`。本期需求**不强制**新开专用导出 API；若实现时发现轮询包过大或字段不全，再单独提接口需求。在那之前，用现有 GET 或只读脚本 dump 即可。

### 4.4 站外导入侧

- 提示词必须是当时的 `docs/rules-prompts.md` 全文（或发布时锁定的版本号/hash），评测报告里记录 **prompt 版本**。
- 外部模型名称、温度、是否一次喂整卷还是分块，必须写入实验元数据。
- 导入失败（JSON 非法、缺 `questions`）计为站外路径失败，**不算全自动的错**，单独入桶 `import_failure`。

## 5. 数据契约（评估用导出）

评估消费的逻辑载荷如下。字段名可在实现时微调，语义不得改。

### 5.1 实验包（一份试卷）

```json
{
  "schema_version": "1",
  "document_id": "uuid",
  "source": { "filename": "...", "page_count": 0 },
  "ocr": {
    "engine": "mineru",
    "markdown": "...",
    "markdown_sha256": "..."
  },
  "prompt": {
    "source": "docs/rules-prompts.md",
    "sha256": "..."
  },
  "full": {
    "task_id": "uuid",
    "pipeline": "full",
    "progress_summary": {
      "llm_n": 0,
      "high_skip_n": 0,
      "markdown_to_json_ms": 0
    },
    "questions": []
  },
  "export": {
    "task_id": "uuid",
    "pipeline": "ocr_export",
    "model": "外部模型名",
    "questions": []
  }
}
```

### 5.2 单题（两边同构）

每题至少包含：

| 字段 | 来源 | 用途 |
|------|------|------|
| `question_no` | `ParsedQuestion.question_no` | **对齐键** |
| `display_order` | 暂存项 | `question_no` 缺失时的次级键 |
| `parsed` | `staged_questions[].parsed` | 完整结构 |
| `skip_or_llm` | 仅全自动；若 progress 可还原 | 区分规则跳过 vs Stage2 |

**禁止**把以下内容当作评估主对象：`knowledge_points`、`chapter_path`、`solution_methods`、`kp_matches`、`difficulty`（难度允许记录但不进入第一期总分）。

### 5.3 对齐规则

1. **主键**：规范化后的 `question_no`（去空白、全角数字转半角、去掉题号前的「一、」等卷面大题前缀是否剥离——实现时固定一种算法并写进评测 README，两边用同一函数）。
2. **次级**：若一边缺 `question_no`，用 `display_order` 对齐，并标记 `aligned_by=order`，此类题在报告中单独列出（对齐不可靠）。
3. **只在一边出现**：入桶 `cut`（漏切 / 多切 / 题号漂移），不进入结构细项打分。
4. **一对多**：全自动把两题合成一题或拆成两题，整组入 `cut`，细项分记为不适用。

对齐完成后再做逐题结构比较；未对齐的题不计「答案对错」，只计切分质量。

### 5.4 落盘路径（已实现）

评测 dump **不走教师导出 API**。全自动压测成功后，或对已有 `task_id` 执行 `--dump-from`，写入：

| 文件 | 内容 |
|------|------|
| `bench/eval/<试卷名>/paper.md` | MinerU `ocr_markdown` 原文 |
| `bench/eval/<试卷名>/full.json` | `{questions:[{question_no, display_order, index, parsed}]}` |
| `bench/eval/<试卷名>/meta.json` | 实验元数据（hash、task_id、slice_timing）；`export` 暂为空 |
| `bench/eval/prompt.md` | 落盘时的 `docs/rules-prompts.md` |
| `bench/eval/manifest.json` | 本轮试卷清单 |

站外 JSON 约定交回为同目录 `export.json`。对齐与规则分：`python scripts/bench_eval_quality.py`（见 `docs/全自动解析质量评估_评测规则.md`）。`bench/eval/` 下试卷内容 gitignore，不入库。

## 6. 评分体系

评分分两层：**规则分**（脚本，可回归）与 **保真分**（LLM 裁判，抽样或全量但须可复现）。

### 6.1 规则分（必须脚本化）

以 Markdown 切片 + Schema 约束为准，不调用裁判。

| 桶 ID | 名称 | 通过条件（摘要） | 主要责任侧 |
|-------|------|------------------|------------|
| `cut` | 切题 | 题号集合与 Markdown 中可解析题号一致；无合并、无漏题、无把解析当新题 | 全自动：chunk/skip；站外：模型漏题 |
| `choice_schema` | 选择题结构 | `question_type=choice`；选项不在 `stem`；`options` 为 A/B/C/D（或卷面实际项数）；多选时 `sub_type=multi` | 两边皆可能 |
| `answer` | 答案 | 选择题答案为字母列表且与卷面【答案】/故选/`$\mathrm{X}$` 一致；填空/解答叶子 `answer` 与原文一致（规范化 LaTeX 空白后比较） | 全自动 skip/recover；站外抄写 |
| `parts` | 解答题树 | 总前提在 `stem`，小问在 `parts`；禁止小问正文留在整题 `stem`；禁止用整题 `analysis` 代替叶子 `analyses` | 全自动 `peel_solution_sub_stems`；提示词第 12 条 |
| `editorial` | 教辅杂质 | 解析中无【分析】【点睛】【详解】标签；无「根据……可求」类思路摘要（与 `slice/clean.rs` 夹具同口径） | 全自动 clean；提示词是否要求剥离 |
| `schema` | JSON 契约 | 字段类型、`correct_answer` 分支、图片仍为 Markdown `![]()`、公式分隔符为 `$` | 导入校验 / Stage2 PATCH |

规则分每桶：`pass` / `fail` / `na`。总分不搞加权排名；报告给出 **桶失败率** 与 **题级失败列表**。

### 6.2 保真分（仅 LLM 裁判）

只问一件事：**JSON 里的题干、选项、答案、解析是否在改写/编造/删减原文。**

裁判输入必须同时包含：

1. 该题 Markdown 原文（或对齐后的切片）
2. 全自动 `parsed`
3. 站外 `parsed`

裁判 **不得** 以「哪边更像好题」为准，必须以 Markdown 为准。

建议输出结构化 JSON（实现时锁定 schema）：

```json
{
  "question_no": "8",
  "markdown_is_source": true,
  "full": { "stem": "faithful|rewritten|missing", "analysis": "faithful|rewritten|invented|truncated", "notes": "" },
  "export": { "stem": "...", "analysis": "...", "notes": "" },
  "prompt_vs_paper": "none|prompt_asks_something_paper_lacks|paper_has_something_prompt_forbids"
}
```

`prompt_vs_paper` 专门抓「提示词要求与卷面事实冲突」（例如提示词要求剥离【分析】，而评估者误以为要保留——此类应对照 `rules-prompts.md` 条文，而不是对照「教辅排版习惯」）。

### 6.3 禁止纳入第一期总分的项

- 文笔是否漂亮、解析是否更短更好懂
- 知识点、章节、方法标签
- 难度
- 耗时、token（可作附录指标，与结构对错分开）

附录可记录全自动 `llm_n`、`high_skip_n`、wall time，用于确认「提速没有以某桶失败率暴涨为代价」。

## 7. 失败分流（评估 → 改哪里）

这是本需求的核心：每一类对照结果必须对应**唯一默认动作**，避免同时改 prompt 和正则。

| 对照结论 | 含义 | 默认动作 | 禁止动作 |
|----------|------|----------|----------|
| 站外对、全自动错 | Markdown 上站外结构正确，全自动切/洗/回填错 | 抽该题 Markdown 进 `src/ai/slice`（或 skip/recover）夹具，先写测试再改脚本 | 改 `rules-prompts.md`「迁就」全自动 |
| 全自动对、站外错 | 规则路径已正确，外部模型没遵守提示词或提示词被模型忽略 | 记录模型/温度；若多份卷重复同一类错，再考虑提示词加硬约束或示例 | 为对齐全自动而放宽 CORE 规则 |
| 两边相对 Markdown 同样错 | 很像提示词或 Schema 教错了（或 OCR 本身错） | **先核对 Markdown 是否已错**（OCR 错 → 不改结构化，记 `ocr_error`）；Markdown 对则开提示词修订任务，并同步 `CORE_PARSE_RULES` 测试 | 只改全自动正则把错误结构「固化」 |
| 两边不同且都与 Markdown 不完全一致 | 各错各的 | 拆成两条失败，分别入上表前两行，禁止平均成「都差不多」 | 用裁判偏好当标准 |
| 未对齐 | 切分不一致 | 只修 chunk / 题号，不比较答案 | 强行按数组下标比题 |
| 导入失败 | 站外 JSON 非法 | `import_failure`；重跑导入或修提示词中的 JSON 转义条款 | 算作全自动回归失败 |

### 7.1 改代码的准入

全自动侧改动（`slice`、`confidence` 跳过、`recover`、PATCH 提示、worker）必须满足：

1. 至少一道来自本评估的失败题成为单元测试夹具（真实 MinerU 片段，可脱敏）。
2. 夹具先红后绿。
3. 10 卷回归集上，**目标桶失败数下降，其它桶不得明显回退**（实现阶段定义「明显」：该桶失败题数增加 ≥ 2 或失败率升 ≥ 3 个百分点，须在报告中解释）。

### 7.2 改提示词的准入

改 `docs/rules-prompts.md` 必须满足：

1. 存在 ≥ 1 条「两边同错」或「站外系统性地违反卷面 + 当前条文」的证据（题号、原文摘录、两边 JSON 摘录）。
2. 条文变更与 `CORE_PARSE_RULES` 的测试锁定同步。
3. **不**由裁判模型直接生成新提示词并覆盖文件。

## 8. 回归集（第一期）

### 8.1 范围

当前压测使用的 **10 份解析卷**（选择题+解答题、含【答案】【解析】的教辅/试卷扫描）为第一期回归集，约 **206 题**。

要求：

- 清单固化：文件名 / `document_id` / 题量 / 全自动 skip 率基线写入评测记录（实现后落到 `bench/` 或 `docs/` 附录，本文不指定路径）。
- 增删试卷必须改清单版本号。
- 评测默认 `--reuse` 已有 OCR，禁止无故重传 PDF。

### 8.2 基线（结构质量，不是速度）

速度基线仅作附录（优化后约 5.6 s/题结构化、skip ≈ 69%、`llm_n` ≈ 64/206）。**第一期验收看结构桶，不看是否更快。**

若某次「优化」让 `editorial` 或 `parts` 失败率明显高于本评估首轮实测，即使更快也视为回归失败。

### 8.3 抽样 vs 全量

| 层 | 第一期 |
|----|--------|
| 规则分 | **全量** 206 题 |
| 保真分 | 优先全量；若裁判成本高，则分层抽样：skip 题与 LLM 题按比例抽，且必须覆盖解答题与选择题；抽样方案写入报告 |
| 人工抽检 | 每个失败桶至少人工看 3 题，防止脚本误报 |

---

## 9. 评测流程（逻辑，非排期）

```text
1. 锁定回归清单与 prompt hash
2. 对每份 document：确保 ocr_markdown 已存在
3. 跑 / 复用 pipeline=full → dump staged_A
4. 同一 markdown 走 ocr_export + 外部模型 + import → dump staged_B
5. 按 §5.3 对齐
6. 跑 §6.1 规则分 → 失败列表
7. （可选）跑 §6.2 裁判 → prompt_vs_paper
8. 按 §7 分流，输出：
     - slice 夹具候选
     - 提示词修订候选（默认空）
     - ocr_error / import_failure
9. 人工确认分流后再改代码或提示词（另一任务）
10. 改完后只重跑结构化（reuse OCR），再出对比报告
```

步骤 9–10 **不属于本需求的实现范围**；本需求只要求步骤 1–8 的规格正确，使后续实现有据可依。

---

## 10. 报告应包含的内容

每份评测报告至少有：

1. 实验元数据：日期、prompt hash、OCR 引擎、外部模型、是否 reuse OCR。
2. 对齐统计：对齐成功数、按题号/按序、仅 A、仅 B。
3. 各桶失败率：全自动、站外、两边同失败。
4. 分流计数：应改 slice / 应改 prompt / OCR 错 / 导入失败。
5. 题级明细：题号、桶、两边摘录、Markdown 摘录（截断可接受）。
6. 附录：skip 率、`llm_n`、耗时（若有）。

报告是给开发看的工作材料，不需要教师可读的评分卡。

## 11. 成功标准（需求验收，不是代码验收）

本文档所定义的体系，在**后续实现完成时**应能回答：

1. 这 10 卷上，全自动相对 Markdown 的切题、选项、答案、`parts`、教辅杂质各错多少？
2. 其中多少是「站外已经对、全自动独有」→ 应进 slice 测试？
3. 其中多少是「两边相对卷面同样错」→ 才允许动 `rules-prompts.md`？
4. 改完一轮后，同一 OCR 上上述桶是否变好、有无回退？

若只能给出「哪边 JSON 更像」、不能引用 Markdown 与分流表，则评测实现不合格。

## 12. 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| 题号 OCR 不稳定（`8.` vs `8、`） | 对齐失败被误判为切题错误 | 规范化函数单一实现；对不齐先人工看 1 卷 |
| 站外一次喂整卷导致漏题 | 站外 `cut` 升高，误伤提示词结论 | 元数据记录喂入策略；漏题单独计 |
| 裁判偏爱「写得漂亮的解析」 | 惩罚忠实摘录 | 提示词强制 `markdown_is_source`；规则分不依赖裁判 |
| 复用 OCR 的第二条 pipeline 尚未产品化 | 评测脚本难写 | 需求允许 dump GET；实现阶段再决定是否加「跳过 OCR、只跑结构化」 |
| 日配额 50 | 不能为评测狂开任务 | 强制 reuse `document_id` |
| 把已保存题拿来比 | 标签与人工编辑污染 | 契约写死只读 staged |

## 13. 已拍板决策（讨论结论，避免实现时重开）

1. **不用双账号。**
2. **Markdown 是事实；站外 JSON 不是 gold。**
3. **导出暂存 `ParsedQuestion`，不导出库内题。**
4. **现有任务 GET 已含评估所需核心字段**；专用导出 API 非本需求前置。
5. **硬检查优先；LLM 只判保真与 prompt_vs_paper。**
6. **裁判禁止自动改 prompt / 正则。**
7. **第一期不评打标。**
8. **不破坏 ocr_export。**
